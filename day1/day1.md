# DAY 1 진행용 프롬프트 — ESS 배터리 수명 예측 모델 전략 수립

아래 프롬프트를 사용해 DAY 1 분석과 제출용 HTML 작성을 진행한다. 이 파일은 작업 지시서이며, 분석 결과는 실제 데이터를 실행해 확인한 뒤 작성한다.

---

## 역할과 목표

당신은 ESS 배터리 데이터 분석 담당자다. 아래 요구사항과 평가 기준을 읽고, **기존 `day1/day1.ipynb`를 분석 작업 파일로 사용하여 수정·보완**하라. Batch 1·2·3에 대한 EDA를 수행하고, 확인한 결과에서 피처 설계와 모델 후보 선정으로 이어지는 DAY 1 모델 설계 전략을 수립하라.

최종 제출문서는 **PDF를 직접 생성하지 말고**, 브라우저에서 열어 인쇄 → PDF로 저장할 수 있는 **`DS-MINI-Design-울산_3반-신현중.html`**로 제작하라. 사용자가 인쇄할 때 저장할 최종 PDF 이름은 **`DS-MINI-Design-울산_3반-신현중.pdf`**이다.

## 파일 배치와 경로 규칙

```text
프로젝트 루트/
├── data/                         # 원본 .mat 데이터
├── 요구사항/                     # 요구사항과 평가 기준
└── day1/
    ├── day1.md                   # 이 작업 지시서
    ├── day1.ipynb                # 분석 코드·출력·해석
    └── output/
        ├── DS-MINI-Design-울산_3반-신현중.html
        └── image/                # 분석에서 생성한 그래프 PNG
```

- 이 문서의 파일 경로는 **프로젝트 루트 기준**이다. 이 문서가 있는 `day1` 폴더에서 수동으로 접근할 때는 요구사항은 `../요구사항/`, 데이터는 `../data/`에 있다.
- 노트북은 현재 실행 폴더와 상위 폴더에서 `data/`, `요구사항/`, `day1/day1.ipynb`가 함께 있는 프로젝트 루트를 찾는다. 프로젝트 루트 또는 `day1` 폴더에서 실행한다.
- 데이터·산출물 경로는 `PROJECT_ROOT`, `DATA_DIR`, `OUTPUT_DIR`, `IMAGE_DIR`, `HTML_PATH`를 사용한다. `os.getcwd()`에 `data`를 단순 연결하거나 실행 폴더에 따라 저장 위치가 바뀌는 코드를 작성하지 않는다.
- 그래프 PNG는 `day1/output/image/`에, 제출용 HTML은 `day1/output/`에 저장한다. 원본 데이터 폴더에는 산출물을 저장하지 않는다.

## 1. 참고 문서와 작업 범위

먼저 다음 파일을 읽고 요구사항을 분석에 반영하라.

- `요구사항/요구사항 문서.md`: DAY 1 EDA 질문, 모델 설계 전략, 제출 형식, Evaluation Criteria.
- `요구사항/추가적인_평가기준.md`: 주장에 맞는 그래프와 해석, 모델 선정 이유, 객관적인 피처 선정 및 파생변수 생성 근거, 다중공선성 처리.
- `요구사항/sample.md`: 프로젝트 설명과 결과 정리의 참고 구조. DAY 1에 해당하는 내용만 활용한다.
- `day1/day1.ipynb`: 기존 데이터 로딩·기본 EDA 코드와 해석을 확인하고 확장한다.

작업 규칙:

1. 분석 코드는 `day1/day1.ipynb`에 작성하고, 셀 실행 결과와 해석을 함께 저장한다. `30-ESSHealth-scratch.ipynb`를 작업 파일로 사용하거나 별도의 분석 노트북을 만들지 않는다.
2. 기존 유효한 코드는 재사용하되, 기존 출력과 설명을 사실로 간주하지 않는다. 데이터에서 다시 계산한 결과에 맞게 교정한다.
3. 이번 작업 범위는 DAY 1의 EDA와 모델 설계다. DAY 2의 최종 모델 학습·튜닝·테스트 성능 보고를 완료한 것처럼 작성하지 않는다.
4. PDF 생성, Slack 제출, GitHub 공개·업로드는 수행하지 않는다.
5. 확인하지 못한 수치·그래프·성능을 만들지 않는다. 분석이 불가능한 부분은 원인과 영향, 후속 확인 사항을 표시한다.

아래 경로는 모두 프로젝트 루트 기준이다. 다음 로컬 파일을 사용한다.

| 용도 | 배치 | 파일 |

| EDA 및 DAY 2 학습 전략 | Batch 1 | `data/2017-05-12_batchdata_updated_struct_errorcorrect.mat` |
| EDA 및 DAY 2 최종 테스트 계획 | Batch 2 | `data/2018-02-20_batchdata_updated_struct_errorcorrect.mat` |

`data/2018-04-03_varcharge_batchdata_updated_struct_errorcorrect.mat`는 이번 대상에서 제외한다.

- 실제 MATLAB 구조, 변수명, 배열 차원, 정책 문자열, 사이클 번호를 먼저 확인한다. 문서의 `QD`는 실제 `summary.QDischarge` 등과 대응 관계를 명시한다.
- 기존 노트북의 Batch 1 전용 로딩을 세 배치 처리로 확장한다. 대용량 파일이므로 배치를 순차 처리하고 필요한 필드만 추출하는 등 메모리 사용을 관리한다.
- `batch_id`와 배치 내 셀 번호를 합쳐 고유 `cell_id`를 만든다. 서로 다른 배치의 동일 번호 셀이 섞이지 않게 한다.
- 셀 단위 메타데이터, 사이클 단위 요약 데이터, 초기 사이클 피처 테이블을 구분한다. 수명 분포와 상관관계는 **셀당 한 행**으로 집계한다.
- 사이클 번호는 실제 제공 필드를 우선 사용한다. `cycles[99]`가 반드시 사이클 100이라는 가정을 하지 말고 인덱스와 실제 번호의 대응을 검증한다.
- 배치별 원본 셀 수, 사용 셀 수, 제외 셀 ID·이유, 사이클 범위, 결측·비정상값, 초기 5/100 사이클 및 `Qdlin` 확보 여부를 표로 정리한다.
- 배치 간 이어서 측정된 동일 물리 셀이 있는지 확인 가능한 식별 정보와 기록을 점검한다. 확인된 중복 셀의 결합·제외 및 데이터 분할 처리 근거를 기록하고, 미확인 사항을 단정하지 않는다.
- 짧은 수명이나 희귀 충전 정책만을 이유로 셀을 삭제하지 않는다. 원본과 정제 결과를 구분하고 삭제·보정 기준을 기록한다.

## 3. EDA 공통 작성 방식

아래 다섯 질문을 **각 Batch별로 분석하고 배치 간 비교**하라. 모든 질문은 다음 순서로 정리한다.

> 질문 → 적합한 그래프·통계 → 실제 확인한 핵심 내용 → 도메인 해석과 한계 → 피처·전처리·모델 전략에 미치는 영향

- 그래프에는 제목, 축 이름·단위, 배치·그룹 범례, 분석 대상 수를 표시한다.
- 배치 비교에는 가능한 한 동일한 축 범위, 구간, 색상 의미를 사용한다.
- 관찰 사실과 원인 가설을 구분한다. 상관관계만으로 인과관계를 확인했다고 쓰지 않는다.
- 그래프 나열로 끝내지 말고 숫자로 뒷받침한 주장과 전략을 연결한다.
- 전체 수명 구간의 열화 곡선은 EDA에 사용할 수 있지만, 예측 시점 이후의 정보는 모델 입력에서 제외한다.

### 질문 1. Cycle Life 분포는 어떻게 생겼는가?

- 배치별 동일 bin의 히스토그램과 박스플롯을 작성한다. 요구 범위인 150~2,300 사이클을 포함하되 범위 밖 관측치가 있다면 별도 표시해 누락하지 않는다.
- 셀 수, 평균, 중앙값, 표준편차, 사분위수, 최솟값·최댓값을 비교한다.
- 장수명 `cycle_life > 1000`, 단수명 `cycle_life < 500`, 나머지 그룹의 수와 비율을 표시한다. 이는 분류 타깃의 550 임계값과 구분한다.
- 유독 수명이 짧거나 긴 셀을 식별하고 정책·용량 곡선·데이터 품질을 점검한다. 이상치의 원인은 확인한 증거 수준에 맞춰 설명한다.
- 배치별 타깃 분포 차이가 평가와 일반화에 미칠 영향을 제시한다.

### 질문 2. 방전 용량은 어떻게 감소하는가?

- 배치별 사이클–방전 용량 곡선과 대표적인 장·단수명 셀 비교를 작성한다. 색상은 실제 `cycle_life` 또는 명시한 수명 그룹에 대응시킨다.
- 초기 용량으로 정규화한 곡선도 검토하고, 초기 기준 용량 계산에 사용한 사이클과 정제 규칙을 설명한다.
- EOL 기준선은 확인한 기준 용량의 **80%**로 계산한다. 기존 코드의 `0.88 * nominal`을 80%라고 표시하는 오류를 바로잡는다. 제공된 `cycle_life`의 정의와 분석용 기준선의 관계도 명시한다.
- 초기 스파이크 등 측정 이상과 실제 말기 열화를 구분한다. 80% 미만의 용량을 일괄 삭제해 EOL 이후 구간이나 knee를 숨기지 않는다.
- 초기/중기/후기 기울기와 열화 가속 여부를 확인한다. Knee point는 변화점 또는 구간별 기울기 등 재현 가능한 탐색 방법과 불확실성을 설명한다.
- 전체 수명에서 구한 knee 위치·말기 기울기는 설명용으로만 사용한다. 예측 시점 이전에 산출할 수 있는 초기 기울기·변동성 등을 입력 후보로 검토한다.

### 질문 3. 초기 ΔQ(V) 곡선에서 수명 차이가 보이는가?

- 실제 사이클 번호를 확인한 뒤 `ΔQ(V) = Q_100(V) - Q_10(V)`를 계산한다.
- `cycles`의 `Qdlin`과 전압 축의 의미·길이·정렬을 점검한다. 1,000포인트, 2.0~3.6V 여부를 검증하고 확인되지 않은 전압 축을 임의로 단정하지 않는다.
- Batch 3의 충전/방전 곡선 시작 위치와 보간 기준 차이를 점검한다. 필요하면 공통 전압 구간에 정렬·보간하고, 처리 전후의 비교 및 사용 가능한 셀 수를 제시한다. 겹치지 않는 구간은 무리하게 외삽하지 않는다.
- 배치별 장수명·단수명 곡선의 대표 사례와 그룹 요약을 비교한다. 해당 그룹이 없거나 표본이 적으면 그대로 표시하고, 분위수 기반 보조 비교는 별도로 명명한다.
- 분산, 최솟값, 평균, 범위 등 후보 통계량을 추출한다. 로그 분산을 사용하면 로그 밑, 수식, 0·결측·무한값 처리 규칙을 명시한다.
- 통계량과 `cycle_life`의 관계를 그래프와 상관계수로 비교해 후보 선정 근거를 제시한다.
- 초기 5사이클 분류를 선택한다면 100–10 ΔQ는 EDA 근거로만 남기고 모델 입력에서 제외한다. 분류용 ΔQ를 검토할 때는 5사이클 이내의 관측치만 사용하고 별도로 타당성을 확인한다.

### 질문 4. 충전 조건(C-rate)과 수명은 어떤 관계인가?

- 정책별 수명 평균·중앙값·분산과 표본 수를 비교한다. 평균 그래프에는 표준편차 등 오차막대의 의미를 명시하고, 개별 셀 분포도 함께 확인한다.
- 정책 문자열에서 1단계 C-rate, 전환 SOC, 2단계 C-rate를 추출하고 파싱 실패를 기록한다.
- 고속 충전과 수명의 관계를 배치별로 비교하며, 전환 SOC·2단계 속도·온도 등 함께 달라지는 조건과 소표본 한계를 설명한다.
- 초기 충전 전류 패턴 또는 초기 충전시간과 초기 열화 속도의 관계를 분석한다. 요약 피처는 선택한 예측 시점 이내에서 계산한다.
- 정책 범주형 인코딩과 수치형 분해 피처의 필요성, 배치 간 미관측 정책 처리 계획을 제시한다.

### 질문 5. 어떤 초기 신호가 수명과 연관되는가?

- 셀 단위 초기 피처–타깃 Pearson/Spearman 상관계수와 주요 산점도를 작성한다. 배치별 결과와 통합 결과를 비교해 배치 효과를 구분한다.
- 초기 QD 수준·변동성·기울기, IR 수준·변화, 온도, 충전시간, ΔQ 통계량, 정책 분해 변수 등을 가용성과 예측 시점에 맞춰 검토한다.
- 상관계수 계산에 사용한 셀 수와 결측 처리 방법을 표시한다. 낮은 선형 상관만으로 비선형 관계가 없다고 단정하지 않는다.
- 피처 간 상관행렬과 필요시 VIF 등으로 다중공선성을 검토한다. 특히 온도 요약값, 충전시간–C-rate, 서로 유사한 ΔQ 파생변수의 중복을 확인한다.
- 중복 피처 제거·대표 변수 선정·규제 적용 등의 처리 방안을 실제 결과와 연결한다. 정제·선택·스케일링은 DAY 2에서 학습 fold 내부에 적합하도록 설계한다.

## 4. 기존 노트북 해석 교정

기존 Markdown 설명도 실행한 코드와 대조해 수정하라.

- 셀 순서로 부여한 색상을 장·단수명 색상으로 해석하지 않는다.
- 박스플롯 whisker 길이를 곧바로 충전 조건의 효과나 예측 난이도의 근거로 삼지 않는다.
- IR 스파이크의 원인을 셀 교체나 특정 전극 구조라고 증거 없이 단정하지 않는다.
- 평균 온도와 수명의 상관관계를 발열에 의한 열화의 인과관계가 확인된 것으로 표현하지 않는다.
- 배치·셀 수·분석 범위가 달라진 뒤에도 기존 평균, 상관계수, 정책 순위가 남아 있지 않게 한다.

## 5. EDA 기반 모델 설계 전략

### 5.1 태스크와 타깃 선택

회귀 또는 분류 중 **하나**를 실제 EDA와 활용 목적에 근거해 선택하고 다른 선택지와 비교한 이유를 설명한다.

| 선택지 | 입력 관측 기간 | 타깃 | DAY 2 평가 계획 |
| --- | --- | --- | --- |
| Regression | 초기 100사이클 이내 | EOL까지의 총 사이클 수 `cycle_life` | MAPE(%), 과제 비교 목표 9.1% |
| Classification | 초기 5사이클 이내 | `label = (cycle_life >= 550).astype(int)`; 1=장수명, 0=단수명 | F1-Score, Accuracy, 과제 비교 목표 Accuracy 95.1%(오차 4.9%) |

- `cycle_life`는 총 수명이다. 이를 그대로 잔여 수명 RUL이라고 쓰지 않는다. 잔여 수명을 다룬다면 관측 종료 사이클과의 관계를 별도로 설명한다.
- 분류는 550 기준의 실제 클래스 비율과 배치별 클래스 존재 여부를 확인한다. 분류에 100사이클 피처를 입력하지 않는다.
- 목표 성능은 요구사항에 제시된 비교 기준으로 표기하며 이번 분석에서 달성한 수치처럼 쓰지 않는다.

### 5.2 피처와 전처리 설계

다음 항목을 갖춘 피처 설계 표를 작성한다.

| 피처/후보 | 원본 변수·계산식 | 사용 사이클 | 관련 EDA 수치·그래프 | 채택/보류/제외 근거 | 결측·이상값·공선성 처리 |
| --- | --- | --- | --- | --- | --- |

- 피처 수에 비해 셀 수가 적은 문제를 고려한다. 많이 만드는 것보다 재현성·해석·중복 제거 근거를 우선한다.
- 셀 ID, 전체 기록 길이, 전체 수명 통계, 말기 곡선, 타깃에서 만든 그룹 등 정답을 드러내는 변수를 입력에서 제외한다. `batch_id`는 배치 비교와 분할 관리에 사용하며 입력 채택은 신중히 판단한다.
- 로그 변환, 결측 대치, 스케일링, 정책 인코딩 및 미관측 범주 처리의 조건과 이유를 명시한다.

### 5.3 후보 모델과 선택 논리

- 단순 기준 모델부터 포함한다. 회귀라면 평균/중앙값 기준 및 Ridge/Elastic Net, 분류라면 다수 클래스 기준 및 Logistic Regression 등을 검토한다.
- 비선형성과 상호작용 근거가 있으면 트리 앙상블 등을 후보로 추가한다. CatBoost 등 범주형 처리 모델은 실제 정책 변수의 구조와 표본 수에 근거해 검토한다.
- 모델별로 **EDA 발견 → 필요한 모델 특성 → 후보 선정 이유 → 예상 위험·검증 방법**을 표로 연결한다.
- 모델 이름만 나열하지 않는다. 소표본 과적합, 규제 강도, 깊이 등 주요 제어 항목의 검토 방향과 피처 제거 비교 계획을 설명한다.
- 최종 성능이 없는 DAY 1에는 우선 검토 후보와 선정 계획을 제시하고, 최적 모델이 확정된 것처럼 쓰지 않는다.

### 5.4 Evaluation Criteria

- Batch 1을 학습 데이터로 사용하고 Batch 1 내 별도 hold-out을 Valid로 둔다. hold-out을 제외한 Batch 1 학습 부분에서 CV 평균을 Train 지표로 보고하는 계획을 명시한다.
- 셀 단위로 분리하고 동일 물리 셀이 여러 분할에 들어가지 않게 한다. 동일 정책 셀 간 정보 공유의 영향을 줄이려면 정책 그룹 기반 hold-out/CV를 검토한다. 일반 셀 무작위 분할만으로 정책 그룹이 분리된다고 설명하지 않는다.
- 고정 난수, 분할 비율·그룹 기준, 분류 시 클래스 확보 가능성 및 소표본 제약을 명시한다.
- Batch 2는 최종 Test로 유지하고, Batch 3는 선택적 추가 검증으로 계획한다. DAY 1의 배치별 탐색 결과는 데이터 특성 설명에 활용하되 Batch 2/3로 피처를 성능 최적화하거나 튜닝하지 않는다. 이들 배치를 이미 탐색했다는 한계도 기록한다.
- 대치·변환·스케일링·피처 선택·튜닝을 학습 데이터 및 CV fold 내부에서 수행하는 파이프라인을 설계한다.
- 평가 표에는 Train(Batch 1 CV), Valid(Batch 1 Hold-out), Test(Batch 2), Gap(Train-Valid), Gap(Valid-Test), Gap(Target-Test)를 포함할 계획을 명시한다. DAY 1 문서에 가짜 성능 숫자를 채우지 않는다.
- Gap은 산식을 명시한다. MAPE는 `Valid-Train`, `Test-Valid`, `Test-9.1%`로, F1/Accuracy는 `Train-Valid`, `Valid-Test`로 정의해 양수가 성능 저하를 의미하도록 한다. Accuracy의 목표 대비 차이는 `95.1%-Test Accuracy`(퍼센트포인트)로 표기하고, F1에는 제공된 원논문 목표가 없다고 표시한다.

### 화면·인쇄 요구사항

- 한국어 문서로 작성하고 `<html lang="ko">`, UTF-8, 내용에 맞는 `<title>`을 설정한다.
- 각 그래프를 `IMAGE_DIR`(`day1/output/image/`)에 의미 있는 이름의 PNG로 저장한다. 예: `q1_cycle_life_distribution.png`, `q2_capacity_degradation.png`. `fig.savefig(..., dpi=200, bbox_inches="tight", facecolor="white")` 등으로 축·범례가 잘리지 않고 A4에서도 읽히도록 저장한다. 노트북 출력에도 동일한 그래프를 표시한다.
- HTML 제작 시 저장한 PNG 파일을 읽어 Base64로 변환하고 `<img src="data:image/png;base64,...">`로 삽입한다. 파일 경로를 HTML 이미지 주소로 참조하지 않는다. 그래프마다 설명에 맞는 `alt`를 지정한다.
- CSS와 그래프를 HTML에 포함해 **HTML 파일 하나로** 열리고 인쇄되게 한다. `image/`는 그래프 원본 관리용이며 제출용 HTML을 여는 데 필수 파일이 아니다. 외부 CDN·웹폰트·네트워크 접근을 필수로 요구하지 않는다.
- 화면에서는 읽기 좋은 여백·글자 크기·표 정렬을 제공한다. 각 그래프에는 관찰 내용과 시사점을 가까이 배치한다.
- `@page { size: A4; margin: 15mm; }`와 `@media print`를 사용한다. 표·그림·캡션이 잘리거나 축소돼 읽기 어려워지지 않도록 폭과 페이지 나눔을 조정한다.
- 표 헤더 반복(`thead { display: table-header-group; }`), 짧은 그림·표·핵심 블록의 `break-inside: avoid`, 필요한 구간의 페이지 나눔을 적용한다. 페이지보다 긴 섹션 전체를 분할 금지하지 않는다.
- 인쇄용 스타일에서 조작 버튼을 숨기고, 배경색 없이도 그래프와 표를 이해할 수 있게 한다.
- 화면 상단에 `window.print()`를 호출하는 “인쇄 / PDF로 저장” 버튼과 다음 안내를 제공한다: **“인쇄 대상에서 PDF로 저장을 선택하고, A4 용지로 확인한 뒤 DS-MINI-Design-울산_3반-신현중.pdf로 저장하세요. 브라우저 머리글·바닥글은 필요하면 해제하세요.”**
- 브라우저 인쇄창의 저장 파일명을 HTML이 강제 지정할 수 있다고 설명하지 않는다. 버튼은 사용자가 누를 때만 인쇄창을 열게 한다.
- **PDF 파일은 생성하지 않는다.** 브라우저의 PDF 저장 API, PDF 변환 도구, 자동 다운로드 코드를 사용하지 않는다.
